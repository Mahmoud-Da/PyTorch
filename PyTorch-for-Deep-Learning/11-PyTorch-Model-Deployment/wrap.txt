*** 272. What is Machine Learning Model Deployment - Why Deploy a Machine Learning Model ***
### **Lecture Summary: What is Machine Learning Model Deployment?**

#### **Definition**

Machine Learning (ML) model deployment is the process of **making your machine learning model available to someone or something else**.

#### **Explanation with Examples**

* **Example 1: Image Classification (FoodVision Mini)**

  * Input: Food images
  * Model: Classifies images into categories like pizza, sushi, steak.
  * Output: Allows a **person** (user) to interact with the model via a mobile app.

* **Example 2: Credit Card Fraud Detection**

  * Input: Financial transaction data
  * Model: XGBoost model determines if a transaction is fraudulent.
  * Output: Used by **another system** (e.g., backend services, databases) to approve or reject transactions.

> Models can interact with both people and systems depending on the use case.

#### **Why Deploy ML Models?**

* **Real-world utility**: It's not enough for a model to work in a notebook—it should be usable in practice.

* **Philosophical idea**:

  > If a machine learning model never leaves a notebook, does it really exist?

* Most models are trained and tested on:

  * Training set
  * Validation set
  * Test set

* But there is a **fourth dataset**:

  * **The real world** — the ultimate test for a model.

#### **Real-world Testing and Feedback Loop**

* To truly evaluate a model, it must be deployed in the real world.
* Real-world issues may not be present in training or test data.
* After deployment:

  1. Monitor the model
  2. Detect issues
  3. Collect new data
  4. Update the model
  5. Redeploy

This creates a **feedback loop** essential for continuous improvement.

---

### **Extended ML Workflow**

Traditional steps:

1. Get data ready
2. Build or use a pre-trained model
3. Define loss function and optimizer
4. Train the model
5. Evaluate the model
6. Save and reload the model

**New step added**:

* **Step X: Deploy and Monitor the Model**

  * Make the model accessible
  * Monitor real-world performance
  * Adjust the model as needed

---

### **Beyond Just Modeling**

ML Engineering is not only about building models:

* It includes **building infrastructure** to support data preprocessing, deployment, and model updates.
* One key component is **deployment code**.

---

### **ML Ops (Machine Learning Operations)**

* ML Ops is a set of practices to:

  * **Deploy**
  * **Maintain**
    machine learning models in **production environments**.

* Focus areas:

  * Reliability
  * Efficiency
  * Scalability

*** 273. Three Questions to Ask for Machine Learning Model Deployment ***
### **Lecture Summary: Types of Machine Learning Model Deployment Scenarios**

#### **Recap of Previous Concepts**

* **Why Deploy ML Models?**

  * To test them in the **real world** (the fourth dataset).
  * While training, validation, and test metrics are useful, **real-world performance** is what truly matters.
  * Deployment reveals **errors not seen during development**.

* **Updated PyTorch Workflow**

  * Original steps: Data → Model → Train → Evaluate → Save
  * New final step: **Deploy and Monitor**

* **ML Engineering vs ML Research**

  * ML Research: Build and test models.
  * ML Engineering: **Make models accessible** to others, includes building infrastructure for deployment and monitoring.

* **ML Ops (Machine Learning Operations)**

  * Extension of ML workflow to include **production-ready deployment and monitoring**.
  * Helps bridge the gap between research and practical use.

---

### **Three Key Questions to Guide Deployment**

#### **1. What is my most ideal machine learning model deployment scenario?**

* **Ideal scenario for FoodVision Mini**:

  * Works **every time** (100% accurate)
  * Works at **speed of light** (real-time response)
* While perfection isn’t practical, setting an ideal goal helps **design the system accordingly**.

#### **2. Where is my model going to go?**

* **Deployment Location Options**:

  * **On-device (Edge)**

    * Model runs on the user’s device (e.g., smartphone).
    * Fast and private.
    * Requires smaller models due to limited compute.
  * **Cloud**

    * Model runs on remote servers accessed over the internet.
    * Allows more complex models due to high compute power.
    * May have network latency but is scalable.

> In practice, many systems use **both**: a small on-device model for quick predictions, and a fallback to a cloud model for more accurate results.

#### **3. How is my model going to function?**

* **Function Modes**:

  * **Online (Real-time)**

    * Model gives predictions instantly as data is received.
    * Example: Take a photo of food → Get prediction immediately.
  * **Offline (Batch)**

    * Model processes data in groups at a later time.
    * Example: Upload 10 photos → Get results after an hour.

> Again, both modes are often combined. Training usually happens **offline**, while predictions are often made **online**.

---

### **Deployment Design Considerations**

* **Prediction Pipeline vs Training Pipeline**:

  * **Prediction pipeline** is usually online (real-time inference).
  * **Training pipeline** is offline (batch processing).
* **Device Limitations**:

  * On-device models must be optimized for memory and speed.
  * Cloud models can be larger but introduce latency.

---

### **Conclusion**

When planning to deploy a machine learning model, consider the following:

1. **Ideal Scenario**: How perfect do you want the experience to be (e.g., speed, accuracy)?
2. **Deployment Target**: Will the model run on-device or in the cloud?
3. **Function Mode**: Should it work in real-time or in batches?

Answering these questions helps guide design choices for infrastructure, user experience, and scalability.

*** 274. Where Is My Model Going to Go? ***
### **Lecture Summary: Deployment Locations — On Device (Edge) vs Cloud**

#### **Recap of Key Deployment Questions**

1. **What is my most ideal ML deployment scenario?**

   * High accuracy (works every time)
   * High speed (as close to real-time as possible)

2. **Where is my model going to go?**

   * On-device (edge)
   * Cloud

3. **How is my model going to function?**

   * Online (real-time)
   * Offline (batch)

---

### **Deep Dive: Where is My Model Going to Go?**

#### **1. On-Device / Edge Deployment**

##### **Definition**:

Model runs directly on the user's hardware (e.g., smartphone, car, IoT device).

##### **Use Cases**:

* **FoodVision Mini**: User takes a photo on their smartphone, prediction is made instantly.
* **Tesla Autopilot**: Model needs to detect obstacles in real time, with no time for cloud round-trips.
* **iOS Features**: Text detection, subject selection from photos, etc., done locally for better experience.

##### **Advantages**:

* **Low latency**: No need to send data over the network.
* **Offline capability**: Works without internet.
* **Privacy**: Data does not leave the device.

##### **Disadvantages**:

* **Limited compute**: Smaller models are needed due to hardware constraints.
* **Limited storage**: Can't deploy large models easily.
* **Device-specific tailoring**: May need different builds for iOS vs Android.

##### **Extra Example**:

* Deploying a PyTorch model to a **Raspberry Pi** for live camera-based inference.

---

#### **2. Cloud Deployment**

##### **Definition**:

Model runs on powerful remote servers (e.g., AWS, Google Cloud, Azure) accessed over the internet.

##### **Use Cases**:

* Handling large, resource-intensive models.
* Centralized inference for multiple clients via APIs.
* Training large models using distributed systems.

##### **Advantages**:

* **Scalable compute**: Use large models and powerful GPUs/TPUs.
* **Centralized maintenance**: Deploy once, use anywhere.
* **Ecosystem integration**: Easily fits into existing cloud-based workflows.
* **Uniform interface**: Can serve models via APIs to multiple platforms.

##### **Disadvantages**:

* **Latency**: Data has to be sent to the server and back, which causes delay.
* **Privacy risks**: Data must leave the user's device.
* **Cost**: If not managed, cloud compute costs can grow rapidly (e.g., auto-scaling misuse).

##### **Example Workflow**:

* Deploy model as an **API**.
* Another program sends input data to the API and receives prediction results.

---

### **On-Device vs Cloud: Trade-offs**

| Feature           | On-Device / Edge            | Cloud                                    |
| ----------------- | --------------------------- | ---------------------------------------- |
| **Latency**       | Very low                    | Higher due to network round-trips        |
| **Privacy**       | High (data stays on device) | Lower (data sent over the internet)      |
| **Compute Power** | Limited                     | Virtually unlimited                      |
| **Scalability**   | Device-specific             | Easily scalable via cloud infrastructure |
| **Offline Use**   | Possible                    | Not possible                             |
| **Model Size**    | Needs to be small           | Can be large and complex                 |
| **Cost**          | Low (once deployed)         | Potentially high if not managed properly |

---

### **Additional Notes and Resources**

* Many systems **combine both** approaches:

  * Inference on device for speed and privacy.
  * Training and advanced processing in the cloud for power and scale.

* Tools and Tutorials Mentioned:

  * **PyTorch on Raspberry Pi**: On-device deployment example.

*** 275. How Is My Model Going to Function? ***
### **Lecture Summary: How is My Model Going to Function? (Online vs Offline Inference)**

---

#### **Recap**

Previously, we explored the **deployment location** of models:

* **On-device (Edge)** vs **Cloud**

Now, we move to the question:

### **"How is my model going to function?"**

The two main options are:

* **Online (Real-Time)**
* **Offline (Batch / Asynchronous)**

---

### **1. Online (Real-Time) Inference**

#### **Definition**:

Predictions are returned **immediately** or with minimal delay when data is input.

#### **Characteristics**:

* Also called **synchronous prediction**
* Used in applications where immediate response is required

#### **Examples**:

* **FoodVision Mini**: User uploads an image, model immediately classifies it (e.g., pizza, steak, sushi)
* **Fraud Detection**: Credit card transactions are classified as legitimate or fraudulent instantly
* **Spam Detection**: Emails or messages are scanned upon arrival
* **Real-Time Translation**: Services like Google Translate return results instantly
* **Self-Driving Cars**: Obstacle detection must happen instantly for safety

#### **Benefits**:

* Fast user experience
* Critical in real-time decision-making
* Essential for safety in high-stakes systems (e.g., autonomous vehicles)

#### **Limitations**:

* Requires low-latency infrastructure
* Can be limited by available compute (especially on-device)
* Needs high system reliability and uptime

---

### **2. Offline (Batch / Asynchronous) Inference**

#### **Definition**:

Predictions are returned **after a delay**, often on a schedule or in large groups.

#### **Characteristics**:

* Also called **asynchronous or batch prediction**
* Often scheduled (e.g., every 10 minutes, hourly, daily)
* Operates on **multiple samples at once**

#### **Examples**:

* **Apple Photos**: Sorts photos into categories (e.g., beach, family) when phone is charging
* **YouTube Recommendations**: Could be updated hourly or daily based on user behavior
* **YouTube Video Indexing**: Extracts topics or tags from uploaded videos in the background
* **Model Training**: Done offline in batch using large datasets

#### **Benefits**:

* Optimized for high throughput
* Efficient use of resources (batch processing is generally cheaper per prediction)
* Can be done during off-peak hours (e.g., while phone is idle or charging)

#### **Limitations**:

* Predictions not immediate
* Not suitable for real-time decision-making
* Can result in outdated or delayed outputs

---

### **Comparative Summary: Online vs Offline Inference**

| Feature           | Online (Real-Time)                          | Offline (Batch / Asynchronous)        |
| ----------------- | ------------------------------------------- | ------------------------------------- |
| **Speed**         | Fast, low-latency                           | Slower, delayed                       |
| **Use Case Fit**  | Real-time response needed                   | Response can be delayed               |
| **Compute Style** | Single or few inputs at a time              | Many inputs at once (batch)           |
| **Optimization**  | For low latency                             | For high throughput                   |
| **Examples**      | Fraud detection, FoodVision Mini, Translate | YouTube recommendations, Apple Photos |
| **Best For**      | Immediate predictions                       | Bulk processing, background tasks     |

---

### **Design Consideration**

Choose **online** when:

* The user expects or needs instant feedback
* Delay negatively impacts user experience or safety

Choose **offline** when:

* You’re processing large amounts of data
* Immediate output isn’t necessary
* System resource usage needs to be optimized

---

### **Mixed Approach**

Just like with **cloud vs edge**, you can **combine online and offline**:

* **Online for inference**, **offline for training**
* **Fallback systems**: On-device model runs first; if uncertain, sends to cloud for more accurate offline processing

---

## **Lecture Summary: Tools and Platforms for Machine Learning Model Deployment**

---

### **Recap**

In the previous videos, we answered:

* **Where will my model go?** (Device vs. Cloud)
* **How will my model function?** (Online vs. Offline)

Now, we explore:

## **What tools and platforms are available to deploy machine learning models?**

---

### **1. On-Device / Mobile / Edge Deployment Tools**

These tools are used when the model runs directly on the user’s device (e.g., phone, embedded system), offering low latency and often greater privacy.

#### **a. Google ML Kit**

* For Android apps or cross-platform mobile development
* Integrates ML models into mobile apps
* Useful for tasks like image labeling, face detection, OCR

#### **b. Apple Core ML**

* Apple's framework for running ML models on iOS/macOS devices
* Requires converting models from PyTorch or TensorFlow using `coremltools`
* Enables real-time on-device inference

---

### **2. Cloud Deployment Platforms**

These are ideal when you need scalable, centralized model access with more compute power.

#### **a. Google Cloud Vertex AI**

* Managed ML platform on Google Cloud
* Supports training, deployment, and monitoring

#### **b. Amazon SageMaker**

* AWS’s end-to-end ML deployment suite
* Highly integrated with AWS services

#### **c. Microsoft Azure Machine Learning**

* Microsoft’s ML platform for training and deployment
* Often used in enterprise settings

#### **d. Hugging Face + Gradient**

* Hugging Face offers `Spaces` for easy deployment
* `Gradient` by Paperspace integrates with Hugging Face and supports cloud GPU inference

---

### **3. General-Purpose API Deployment Tools**

These are used when deploying a model as a web-accessible API.

#### **a. FastAPI**

* Lightweight Python web framework for building RESTful APIs
* Suitable for exposing ML models through endpoints
* Simple, quick to prototype

#### **b. TorchServe**

* PyTorch’s native deployment framework
* Designed specifically for serving PyTorch models
* More robust and feature-rich than FastAPI for ML use cases
* Supports both eager and TorchScript models

#### **TorchScript**:

* A way to convert PyTorch models into a scriptable format
* Enables deployment in environments **without Python**

---

### **4. ONNX (Open Neural Network Exchange)**

* **Open standard** for machine learning model interoperability
* Allows converting and running models across frameworks (e.g., PyTorch → ONNX → TensorFlow)
* Use case: Deploying models in environments like **browsers**, **mobile devices**, or **hardware accelerators**
* **ONNX Web Runtime**: Run ONNX models directly in the browser (JavaScript/WebAssembly support)

---

### **5. Extra Resources**

The lecture references several additional guides and tools:

* **Apple Core ML Tools**: For converting PyTorch models to `.mlmodel` for Apple devices
* **Hugging Face Spaces**: For fast app demos using Gradio or Streamlit
* **ONNX Runtime in Browsers**: Powerful for deploying models in web apps
* **Blog Articles**:

  * *Deploying a PyTorch model to the edge with Raspberry Pi*
  * *Moving ML inference from Cloud to Edge* by Joe Christian Burgum

These are available in the course's **extra curriculum section** under PyTorch deployment resources.

---

### **Key Takeaways**

* The best deployment tool or platform **depends on your use case**:

  * For **mobile** apps → Use Core ML or ML Kit
  * For **scalable, cloud-based access** → Use Vertex AI, SageMaker, or Azure
  * For **fast prototyping APIs** → Use FastAPI
  * For **production-grade serving** → Use TorchServe
  * For **cross-platform or browser deployment** → Use ONNX

* Each of these tools requires **different levels of setup and infrastructure knowledge**.

* You’ll likely encounter different tools depending on the project, team, or company you work in.

## 2. What Is a Feature Extractor?

* A **feature extractor** in the context of **transfer learning**:

  * Uses a pre-trained model’s base layers (frozen)
  * Replaces the output (classifier) layer with a custom head for the specific task
* Benefits:

  * Leverages previously learned patterns

*** 294. Creating a Function to Make and Time Predictions with Our Models ***

## **Lecture Notes: Implementing `pred_and_store` Function for Prediction Timing**

---

### **1. Objective**

* Build a **comprehensive function (`pred_and_store`)** to:

  * Measure **latency per sample** for **ViT** and **EfficientNet B2**.
  * Store **prediction details** for each image in the test dataset.
* Purpose:

  * Compare inference speed between the two models.
  * Gather additional evaluation metrics for analysis.

---

### **2. Imports and Setup**

* **Required Libraries**:

  * `from PIL import Image` – Open images.
  * `from pathlib import Path` – Handle file paths.
  * `import torch` – Model and tensor operations.
  * `from timeit import default_timer as timer` – Measure inference time.
  * `from tqdm.auto import tqdm` – Progress bar.
  * `from typing import List, Dict` – Type hints for clarity.

---

### **3. Function Design: `pred_and_store`**

* **Goal**: Return a **list of dictionaries**, one per test image.
* **Parameters**:

  * `paths`: List of image file paths.
  * `model`: Trained PyTorch model.
  * `transform`: Preprocessing transforms for model.
  * `class_names`: List of class labels.
  * `device`: Defaults to `cuda` if available, else `cpu`.

---

### **4. Steps to Implement the Function**

#### **Step 1: Function Header and Device Setup**

-------------------code----------------------
def pred_and_store(
    paths: List[Path],
    model: torch.nn.Module,
    transform,
    class_names: list,
    device: torch.device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
) -> List[Dict]:
-------------------code----------------------

---

#### **Step 2: Initialize Data Structure**

* Create an empty list to store prediction results:

-------------------code----------------------
pred_list = []
-------------------code----------------------

---

#### **Step 3: Loop Through Image Paths**

* Use `tqdm` for progress visualization:

-------------------code----------------------
for path in tqdm(paths):
-------------------code----------------------

---

#### **Step 4: Create Empty Dictionary per Sample**

* Initialize a dictionary to store details for each image:

-------------------code----------------------
predict = {}
-------------------code----------------------

---

#### **Step 5: Extract Metadata from File Path**

* Store:

  * **Image path**.
  * **Ground truth class** (from parent directory name).

-------------------code----------------------
predict["image_path"] = str(path)
class_name = path.parent.stem
predict["class_name"] = class_name
-------------------code----------------------

---

#### **Step 6: Start Timer**

-------------------code----------------------
start_time = timer()
-------------------code----------------------

---

#### **Step 7: Open Image**

-------------------code----------------------
image = Image.open(path)
-------------------code----------------------

---

#### **Step 8: Apply Transforms and Move to Device**

* Add batch dimension and send to target device:

-------------------code----------------------
image_transformed = transform(image).unsqueeze(0).to(device)
-------------------code----------------------

---

#### **Step 9: Prepare Model for Inference**

* Send model to device and set evaluation mode:

-------------------code----------------------
model = model.to(device).eval()
-------------------code----------------------

---

#### **Step 10: Perform Forward Pass**

* Enable inference mode:

-------------------code----------------------
with torch.inference_mode():
    pred_logit = model(image_transformed)
-------------------code----------------------

* Compute **prediction probabilities**:

-------------------code----------------------
pred_probabilities = torch.softmax(pred_logit, dim=1)
-------------------code----------------------

* Find **predicted label and class**:

-------------------code----------------------
pred_label = torch.argmax(pred_probabilities, dim=1).cpu()
pred_class = class_names[pred_label]
-------------------code----------------------

---

#### **Step 11: Store Predictions in Dictionary**

* **Prediction probability** (max value):

-------------------code----------------------
predict["pred_prob"] = round(pred_probabilities.max().cpu().item(), 4)
-------------------code----------------------

* **Predicted class**:

-------------------code----------------------
predict["pred_class"] = pred_class
-------------------code----------------------

---

#### **Step 12: End Timer and Store Time**

-------------------code----------------------
end_time = timer()
predict["time_for_pred"] = round(end_time - start_time, 4)
-------------------code----------------------

---

#### **Step 13: Check Correctness**

-------------------code----------------------
predict["correct"] = (class_name == pred_class)
-------------------code----------------------

---

#### **Step 14: Append Dictionary to List**

-------------------code----------------------
pred_list.append(predict)
-------------------code----------------------

---

#### **Step 15: Return Results**

-------------------code----------------------
return pred_list
-------------------code----------------------

---

### **5. Expected Output**

* A list of dictionaries like:

-------------------code----------------------
[
  {
    "image_path": "...",
    "class_name": "steak",
    "pred_class": "steak",
    "pred_prob": 0.9823,
    "time_for_pred": 0.0345,
    "correct": True
  },
  ...
]
-------------------code----------------------

---

### **6. Next Steps**

* Use this function on:

  * **EfficientNet B2 model**.
  * **ViT model**.
* Calculate:

  * **Average prediction time per sample**.
  * Compare against **performance metrics**.
* Store in each model’s **statistics dictionary**:

  * `avg_prediction_time`.

#### **Key Takeaways**

* This function combines:

  * Timing.
  * Prediction accuracy.
  * Confidence scores.
  * Organized output for analysis.
* Essential for evaluating **trade-off between speed and accuracy** before deployment.

*** 301. Creating a Predict Function to Map Our Food Vision Mini Inputs to Outputs ***
## **Lecture Notes: Implementing the Predict Function for Grading Demo**

### **Overview**

* Goal: Create a **workflow** for grading demo that:

  * Inputs **images of food**
  * Uses a **predict function** to map images → outputs
  * Outputs:

    * Dictionary of **class names → prediction probabilities**
    * **Prediction time** (for evaluating model speed)

---

### **Steps to Implement**

#### **1. Start Timer**

-------------------code----------------------
start_time = time.time()
-------------------code----------------------

---

#### **2. Transform Input Image**

* Apply **FNet B2 transforms** to the image for compatibility with the model.
* Add **batch dimension** since images typically lack it:

-------------------code----------------------
image = fnet_b2_transforms(image).unsqueeze(0)
-------------------code----------------------

---

#### **3. Model Setup**

* Switch model to **evaluation mode**:

-------------------code----------------------
fnet_b2.eval()
-------------------code----------------------

* Enable **inference mode** (no gradients needed):

-------------------code----------------------
with torch.inference_mode():
-------------------code----------------------

---

#### **4. Forward Pass & Compute Probabilities**

* Pass transformed image through model:

-------------------code----------------------
logits = fnet_b2(image)
-------------------code----------------------

* Apply **Softmax** to get probabilities:

-------------------code----------------------
pred_probs = torch.softmax(logits, dim=1)
-------------------code----------------------

---

#### **5. Convert to Dictionary**

* Use class names and probabilities to create a dictionary:

-------------------code----------------------
pred_dict = {class_names[i]: float(pred_probs[0][i]) for i in range(len(class_names))}
-------------------code----------------------

Example:

-------------------code----------------------
{
  "steak": 0.61,
  "sushi": 0.30,
  "pizza": 0.09
}
-------------------code----------------------

---

#### **6. Calculate Prediction Time**

-------------------code----------------------
end_time = time.time()
pred_time = round(end_time - start_time, 4)
-------------------code----------------------

---

### **Testing the Predict Function**

1. Get random image from test dataset:

-------------------code----------------------
test_data_paths = list(Path("test_dir").glob("*/*.jpg"))
random_image_path = random.sample(test_data_paths, k=1)[0]
-------------------code----------------------

2. Open image using **PIL**:

-------------------code----------------------
image = Image.open(random_image_path)
-------------------code----------------------

3. Call **predict function**:

-------------------code----------------------
pred, pred_time = predict(image)
-------------------code----------------------

4. Print results:

-------------------code----------------------
print(f"Predicting on image at path {random_image_path}")
print(pred)
print(f"Prediction time: {pred_time}s")
-------------------code----------------------

**Example Output:**

-------------------code----------------------
Predicting on image at path data/test/steak.jpg
{'pizza': 0.1, 'steak': 0.8, 'sushi': 0.1}
Prediction time: 0.013s
-------------------code----------------------

---

### **Observation**

* Prediction times are around **0.013s**, which is fast.

### **Why Create Examples?**

* If users do not have an image ready, examples allow them to try the model.
* Examples make the interface user-friendly and showcase model performance.

---

### **Step 7.3 – Creating a List of Example Images**

* Gradio accepts **examples** as a parameter in the interface.
* Format: **list of lists**, where each sub-list represents one set of inputs.
* Documentation shows that examples can be passed directly in the `Interface` class.

---

#### **Implementation**

* Generate a list of random image file paths from the test dataset.
* Convert paths to strings (Gradio prefers strings for file paths).
* Example code:

-------------------code----------------------
import random

# Assume test_data_paths is already populated with image paths
example_list = [[str(file_path)] for file_path in random.sample(test_data_paths, k=3)]

print(example_list)
-------------------code----------------------

**Explanation:**

* `random.sample(test_data_paths, k=3)` → Selects 3 random image paths.
* `str(file_path)` → Converts POSIX path to string.
* Wrap in **list of lists**: `[[...]]` as required by Gradio.

---

### **Result**

* `example_list` will look like:

-------------------code----------------------
[['data/test/steak.jpg'], ['data/test/sushi.jpg'], ['data/test/pizza.jpg']]
-------------------code----------------------

* Each list contains one image path for the interface.

---

### **Next Challenge**

* **Build a Gradio Interface** using:

  * **Function:** `predict` (maps image → prediction).
  * **Inputs:** `gr.Image()` (Gradio image component).
  * **Outputs:** Likely `gr.Label()` or similar (to display class probabilities).
  * **Examples:** `example_list`.

**Basic Structure:**

-------------------code----------------------
import gradio as gr

demo = gr.Interface(
    fn=predict,
    inputs=gr.Image(type="pil"),
    outputs=gr.Label(num_top_classes=3),
    examples=example_list
)

demo.launch()
-------------------code----------------------

**Key Notes:**

* Handling **two outputs** (dictionary + prediction time) requires a custom output or `gr.JSON()` for dictionary and `gr.Textbox()` for time.
* Consider splitting outputs into two separate components:

  * Class probabilities → `gr.Label()`.
  * Prediction time → `gr.Textbox()`.

* Stores:

  * **Code** (Python scripts, Gradio/Streamlit apps)
  * **Models**
  * **Datasets**
* Uses:

  * **Git LFS (Large File Storage)** for files >10 MB (e.g., model weights, images, videos)

    * EfficientNetB2 model (29 MB) → Requires Git LFS.

---

#### **Key Characteristics**

* Similar to **GitHub**, but specialized for machine learning.
* Spaces = **Repositories** focused on:

  * Models
  * Datasets
  * Interactive demos

---

### **Why is File Structure Important?**

* Hugging Face Spaces automatically deploys your app based on **specific files** in the repository.
