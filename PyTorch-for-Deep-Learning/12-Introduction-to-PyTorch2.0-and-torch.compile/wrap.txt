*** 329. Introduction to PyTorch 2.0 ***
**Lecture Summary: Introduction to PyTorch 2.0**

**1. Overview of PyTorch 2.0 Release**

* PyTorch 2.0 officially released, with the primary improvement focused on speed.
* The key new feature is `torch.compile`, a backward-compatible function that compiles models to optimize performance.
* After creating a model, passing it to `torch.compile` returns a compiled model that offers speed improvements during training and inference, especially on newer GPUs.

**2. Performance Gains**

* PyTorch tested `torch.compile` on 163 open-source models (from Huggingface Transformers, timm, Torchvision, and TorchBench).
* Tests used mixed precision (automatic mixed precision, Float16) and Float32 training.
* Results showed an average speed increase of 43% in training on Nvidia A100 GPUs.
* Personal benchmarks showed:

  * Larger batch and data sizes benefit more from `torch.compile`.
  * The first training epoch is slower, but subsequent epochs run faster.
  * Speed improvements observed were about 10% on local RTX 40 and A100 GPUs.
* Further exploration needed with mixed precision training, transformer architectures, and longer training runs, where bigger gains are expected.

**3. Technologies Behind `torch.compile`**

* `torch.compile` integrates several components:

  * Torch Dynamo
  * Aot Autograd
  * Torch Inductor
* Two main optimization techniques it offers:

  1. **Fusion (Operator Fusion)**
  2. **Graph Capture (Graph Tracing)**

**4. Fusion (Operator Fusion)**

* Fusion combines multiple operations into fewer operations to reduce overhead.
* Modern GPUs have very high compute power; the bottleneck is often memory bandwidth (speed of moving data between CPU and GPU).
* Fusion minimizes how often intermediate results are written to and read from memory, reducing bandwidth costs.
* Analogy:

  * Without fusion: Adding ingredients one by one and blending repeatedly.
  * With fusion: Adding all ingredients first, then blending once — more efficient.

**5. Graph Capture (Graph Tracing)**

* Graph capture records the sequence of operations in advance.
* Without it, operations are interpreted and executed one-by-one, causing overhead.
* Analogy:

  * Without graph capture: Driving in a new area, thinking about every turn as you go.
  * With graph capture: Driving in your own neighborhood, knowing the route ahead of time.
* Upfront time is spent recording the graph, but later executions are faster.

**6. Additional Resources**

* For a deeper understanding of fusion, memory bandwidth, and overhead, see "Making Deep Learning Go BR from First Principles" by Horace Hare.

**7. Other Notable PyTorch 2.0 Features**

* Faster Transformers is now stable, improving transformer-style model speed.
* Universal device setup introduced via a context manager or global setting.
* Enhanced Metal Performance Shaders improve PyTorch support on Mac.
* Domain-specific library upgrades in:

  * Torchvision
  * Torchtext
  * Torchrec
  * Torchaudio
  * And others.

### 4. New PyTorch 2.0 Feature: `set_default_device`

* Introduces **context manager** and **global device setting**.
* **Benefit**: Automatically places new tensors/models on the target device without calling `.to()`.

---

#### 4.1 Using a Context Manager

-------------------code----------------------
import torch

device = "cuda" if torch.cuda.is_available() else "cpu"

with torch.device(device):
    layer = torch.nn.Linear(20, 20)
    print(layer.weight.device)  # cuda:0
    data = torch.randn(128, 20)
    print(data.device)          # cuda:0
-------------------code----------------------

* All objects created inside the `with` block are placed on the chosen device.
* Requires **PyTorch ≥ 2.0**.

---

#### 4.2 Setting a Global Default Device

-------------------code----------------------
import torch

device = "cuda" if torch.cuda.is_available() else "cpu"
torch.set_default_device(device)

layer = torch.nn.Linear(20, 20)
print(layer.weight.device)  # cuda:0

data = torch.randn(128, 20)
print(data.device)          # cuda:0
-------------------code----------------------

* All subsequent PyTorch objects (created after this call) are placed on the chosen device.
* Also requires **PyTorch ≥ 2.0**.

---

#### 4.3 Switching Back to CPU

-------------------code----------------------
torch.set_default_device("cpu")
-------------------code----------------------

* Reverts default device to CPU.
* Useful for debugging or running parts of code without GPU.

---

### 5. Advantages

### 6. Function for Model and Transforms

-------------------code----------------------
def create_model(num_classes=10):

    Create a ResNet-50 model with appropriate transforms.

    model.fc = torch.nn.Linear(in_features=2048, out_features=num_classes)

    return model, transforms
-------------------code----------------------

*** 339. Discussing How to Get Better Relative Speedups for Training Models ***
## PyTorch 2.0 — Improving Relative Speedups

### 1. Function Recap

* **`create_model`**:

  * Creates a **ResNet-50** model
  * Applies **ImageNet transforms** matching pretrained weights
* Purpose: Provide both model and transforms in one step

---

### 2. Key Idea — GPU Utilization and Relative Speedups

* **Relative speedups** are most noticeable when **a large portion of the GPU is in use**.
* **Bandwidth costs** (data transfer from CPU to GPU) are a major training bottleneck.
* **Operator Fusion**:

  * Combines multiple operations into one to reduce memory writes/reads
  * Reduces bandwidth usage
* **Graph Capture**:

  * Records the computation graph ahead of time
  * Avoids repeatedly looking up operations during execution
  * Not directly about bandwidth, but improves execution efficiency

---

### 3. Practical Guidelines for Better GPU Usage

**General principle:** Keep as much data as possible on the GPU and avoid unnecessary transfers.

#### 3.1 Increase Batch Size

* Standard training often uses **batch size = 32**.
* Larger GPUs allow **larger batches**: 128, 256, 512, etc.
* Multiples of 8 are recommended (for hardware alignment).
* Larger batches mean:

  * More data processed per GPU operation
  * Better parallelism

#### 3.2 Increase Data Size

* Instead of small images (e.g., 32×32), use larger ones:

  * 224×224 (common for ImageNet models)
  * 336×336 for higher resolution tasks
* Can also increase **embedding sizes** for non-image data.

#### 3.3 Increase Model Size

* Move from smaller models (\~1M parameters) to larger ones (10M+ parameters).
* Today’s "small" models may still benefit from larger GPU workloads.

#### 3.4 Decrease Data Transfer

* Transfer only what’s needed to the GPU.
* Use **operator fusion** to avoid intermediate CPU-GPU transfers.
* Prefetch and load data efficiently.

---

### 4. Why Bigger Workloads Can Still Be Faster (Relative Gains)

* Increasing batch size, model size, and image size **does not increase training time linearly**.
* Example (illustrative):

  * Small model, small batch → 10 minutes
  * Larger model, larger batch → more data, but only 2× training time due to parallel GPU computation
* **GPU parallelism** allows more work in the same time window.

---

### 5. Visualization Example

* Small workload: 1 block of data → 10 minutes
* Larger workload: 6× data, 2 GPUs → only 2× time, due to parallel processing

### 6. Further Reading

### 7. Summary of Strategies for Better Relative Speedups

* **Increase**:

  * Batch size
  * Data size
  * Model size
* **Decrease**:

  * CPU–GPU data transfers

*** 340. Setting the Batch Size and Data Size Programmatically ***
## GPU Memory Utilization and Dynamic Batch/Image Sizing in PyTorch

### 1. Core Principle

* **Relative speedups** are most noticeable when **a large portion of the GPU is in use**.
* As datasets and models grow, they may not fit on a single GPU (e.g., NVIDIA A100).
* This is a **universal principle** — not specific to PyTorch 2.0:

  * Applies to all PyTorch versions
  * Applies to all GPU-based models
  * Goal: Use as much GPU capacity as possible

---

### 2. Why Check GPU Memory Programmatically

* The more GPU memory available:

  * The larger the **batch size** can be
  * The larger the **dataset/image size** can be
* Avoids trial-and-error crashes from CUDA out-of-memory errors.
* Enables adaptive settings based on hardware.

---

### 3. Measuring GPU Memory in PyTorch

**Method:** `torch.cuda.mem_get_info()`

* Returns `(free_memory, total_memory)` in bytes.
* **Free memory** = `total_memory - used_memory`
* Convert bytes to gigabytes for readability:

  -------------------code----------------------
  free_gb = free_memory * 1e-9
  total_gb = total_memory * 1e-9
  -------------------code----------------------
* Use these values to decide training parameters.

---

### 4. Example: Dynamic Batch and Image Size

**Logic:**

* If **free memory ≥ 16 GB**:

  * `batch_size = 128`
  * `image_size = 224`
* Else:

  * `batch_size = 32`
  * `image_size = smaller value` (e.g., 128–192)
* Values should be tuned per hardware and dataset.

**Why:**

* Large batch sizes and image sizes increase GPU utilization.
* Smaller sizes prevent memory overflow.

---

### 5. Adjusting Data Transforms

When `image_size` changes, update preprocessing transforms accordingly:

-------------------code----------------------
transforms.Resize(image_size)
transforms.CenterCrop(image_size)
-------------------code----------------------

* Ensures input dimensions match what the model expects.
* Prevents shape mismatch errors.

---

### 6. Hardware-Specific Values

* Example: On NVIDIA A100 (40 GB memory), free memory ≈ 41 GB → batch size 128 is safe.
* On smaller GPUs, values must be reduced to avoid OOM errors.
* Always adapt settings to:

  * GPU total memory
  * Dataset size
  * Model architecture

---

### 7. Key Takeaways

* Use programmatic memory checks to set batch/image sizes dynamically.
* Always update transforms when data dimensions change.
* Avoid fixed hyperparameters that don’t scale across hardware.
* Principle applies beyond PyTorch 2.0 — relevant to all GPU workloads.

*** 341. Getting More Potential Speedups with TensorFloat-32 ***
## TensorFloat-32 (TF32) in PyTorch

### 1. Overview

* **TF32** = **TensorFloat-32**
* Developed by **NVIDIA** to bridge:

  * **Float32** (higher precision)
  * **Float16** (faster computation)
* Combines:

  * Accuracy benefits of Float32
  * Speed benefits of Float16

---

### 2. Recap of Float32 vs Float16

* **Float32**:

  * Represents numbers with 32 bits
  * More precision → more accurate models
  * Slower computation due to more bits to process
* **Float16**:

  * Represents numbers with 16 bits
  * Less precision → potential accuracy trade-off
  * Faster computation due to fewer bits

---

### 3. Why TF32 Exists

* Goal: **Balance precision and speed** in GPU computations
* TF32:

  * Uses Float32’s *range*
  * Uses reduced precision similar to Float16 (10 bits instead of 23 bits)
* Often improves **training speed** without major accuracy loss

---

### 4. Hardware Requirements

* Available on NVIDIA GPUs with architecture **Ampere (2020)** or newer
* Example: **A100 GPU** (available in Google Colab Pro at time of recording)
* GPU compatibility can be checked via its compute capability score:

  * **TF32 support**: `score >= 8.0`

---

### 5. TF32 in PyTorch

* By default:

  * **PyTorch ≤ 1.11**: `torch.backends.cuda.matmul.allow_tf32 = True`
  * **PyTorch ≥ 1.12**: Default set to **False**

    * Reason: Consistency across hardware and avoiding unexpected result differences
* Can be enabled manually for matrix multiplications on CUDA:

  -------------------code----------------------
  import torch
  torch.backends.cuda.matmul.allow_tf32 = True
  -------------------code----------------------

---

### 6. Checking and Enabling TF32

**Example check:**

-------------------code----------------------
import torch

cc_major, cc_minor = torch.cuda.get_device_capability()
score = cc_major + cc_minor / 10
print(f"Using GPU with score {score}")

if score >= 8.0:
    print("Enabling TensorFloat-32")
    torch.backends.cuda.matmul.allow_tf32 = True
else:
    print("TensorFloat-32 not available on this GPU")
-------------------code----------------------

---

### 7. When to Use TF32

* Use TF32 when:

  * You want potential speedups in matrix multiplication-heavy models (e.g., neural networks)
  * Your GPU supports Ampere architecture or newer
* Avoid or test carefully if:

  * You require bitwise reproducibility across different hardware
  * You see accuracy differences that matter for your application

---

### 8. Key Takeaways

* **TF32** is a hardware-level optimization by NVIDIA
* Provides a middle ground between Float32 precision and Float16 speed
* Can be enabled in PyTorch for matrix multiplication on supported GPUs
* Check compatibility before enabling
* Default behavior changed in PyTorch 1.12 — now **False** by default

### 2. Purpose of DataLoaders

* DataLoaders:

  * Handle **batching** of data
  * **Shuffle** data for training to avoid memorization of order
  * Use multiple **CPU workers** to load data in parallel
  * Feed data efficiently to the **GPU**

---

### 3. Number of Workers

* **Definition**: Number of CPU cores/threads used for loading data in parallel
* **Goal**: Increase data loading speed to avoid GPU idle time
* **General practices**:

  * Set `num_workers` to the **CPU count** for maximum parallelism
  * Example:

    -------------------code----------------------
    import os
    NUM_WORKERS = os.cpu_count()
    -------------------code----------------------
* **Caveat**:

  * Performance may **not always scale** with more workers
  * General rule of thumb:

    * Around **4× number of GPUs** is often sufficient
    * Example: 1 GPU → 4 workers may be enough
  * Best to **experiment** for optimal value on your hardware
* **Google Colab note**:

  * CPU count can vary:

    * Free tier may have \~2 CPUs
    * Pro/Premium tier can have 12+ CPUs

---

### 4. Creating DataLoaders

**Code Example:**

-------------------code----------------------
from torch.utils.data import DataLoader

# Training DataLoader
train_dataloader = DataLoader(
    dataset=train_dataset,
    batch_size=128,       # Adjustable depending on GPU memory
    shuffle=True,         # Shuffle training data
    num_workers=NUM_WORKERS
)

# Test DataLoader
test_dataloader = DataLoader(
    dataset=test_dataset,
    batch_size=128,       # Same batch size for test
    shuffle=False,        # No need to shuffle for evaluation
    num_workers=NUM_WORKERS
)
-------------------code----------------------

    * Loss function: `CrossEntropyLoss`
    * Optimizer: Adam (`lr = 0.003`)

**Compilation timing logic:**

-------------------code----------------------
import time
compile_start_time = time.time()
compiled_model = torch.compile(model)
compile_end_time = time.time()
compile_time = compile_end_time - compile_start_time
-------------------code----------------------

---

### 3. Important Notes

* The **first epoch** may take longer because:

  * `torch.compile` performs **graph capture** and **operator fusion**.
  * Optimizations happen during the first pass through the model.
* Compilation itself (the line `torch.compile(model)`) is fast; optimization happens in training.

---

### 4. Common Pitfalls and Fixes

* **Device mismatch**: Ensure the compiled model is on the correct device.

  -------------------code----------------------
  compiled_model.to(device)
  -------------------code----------------------
* **Naming errors**: Training the wrong variable can cause zero accuracy.

  * Mistake: `train(compiled_model)` vs `train(compile_model)` (typo).
  * One-character typos can silently break accuracy without causing code errors in some environments.
* Use an IDE or linting to catch such issues.

---

### 5. Results (Example on A100 GPU)

| Metric                  | Without Compile   | With Compile                     |
| ----------------------- | ----------------- | -------------------------------- |
| Training Epoch 1 Time   | \~75 sec          | Longer (\~1st pass optimization) |
| Training Subsequent Avg | \~71 sec          | \~63 sec (≈ 10% faster)          |
| Test Epoch Time         | \~7.69 sec        | Slightly faster                  |
| Accuracy (Test)         | \~87% (after fix) | \~87%                            |

---

### 6. Observations

* **Speed gain**: \~10% faster training epochs after the first optimization.
* **Accuracy**: Matches Experiment One after fixing the typo.
* **Key lesson**: Small coding mistakes can completely change results; always verify with known-good code.

---

### 7. Takeaway

* `torch.compile` offers noticeable speed improvements with minimal code change.
* Ensure correctness first—speed optimizations are only valuable if the model trains properly.
* Longer training runs will show more pronounced benefits from `torch.compile`.
